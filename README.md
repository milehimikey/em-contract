# em-contract

TypeSpec intelligence for [em](https://github.com/milehimikey/em)-generated contracts: bind a
model-owned contract to real HTTP/async specs **without forking or copying it**.

```
┌────────────────────────── em (the model owns the shapes) ──────────────────────────┐
│                                                                                    │
│  model.em ── em api generate ──▶ contracts/<key>.tsp     (pure TypeSpec, no deps)  │
│          └── em export ────────▶ export.json             (versioned model data)    │
│                                                                                    │
└────────────────────────────────────────────────────────────────────────────────────┘
                     │ generated contract                │ export document
                     ▼                                   ▼
┌───────────────────────── em-contract (this tool owns TypeSpec) ────────────────────┐
│                                                                                    │
│  em-contract augment export.json ──▶ augments.tsp   (@@correlationId/@@header      │
│                                                      candidates from DCB tags)     │
│  bind init / bind check             (planned — waits on em 1.22 Wave 1)            │
│                                                                                    │
└────────────────────────────────────────────────────────────────────────────────────┘
                     │ contract + binding files (one TypeSpec compilation)
                     ▼
     your toolchain: @typespec/openapi3 ──▶ OpenAPI    typespec-asyncapi ──▶ AsyncAPI 3.0
```

## The mission boundary

em ships **interface-as-data**: `em api generate` writes a deterministic, dependency-free
TypeSpec contract from a model's `public` surface to `<model dir>/contracts/<model key>.tsp`,
and `em export` ships the versioned JSON document behind it. em never compiles TypeSpec and
takes no emitter config (owner ruling, 2026-11-07 — a config that changes emission would
break `em api check`'s contract-currency guarantee: the generated text must be a pure
function of the public surface).

**em-contract owns the TypeSpec side of the line.** It depends on `@typespec/compiler`
(pinned exact — pre-1.0 churn in emitter-adjacent APIs is a known risk, held by the living
spike test) and exists so that teams never fork, copy, or hand-edit a generated contract.

The division of labor, in one line: **shapes are model-owned** (generated, regenerated,
byte-compared by `em api check`); **protocol is binding-owned** (hand-authored TypeSpec that
*augments* the contract: routes, channels, envelopes, formats, headers).

## How a binding project fits together

A generated contract is plain TypeSpec — one namespace, models for public events/views,
`interface Commands` / `interface Views` ops, no imports, no decorators:

```typespec
// GENERATED by em api generate — do not hand-edit.
namespace Pricing {
  model SellingPriceDesignated {
    /** DCB identity tag */
    priceId: string;
    /** DCB identity tag */
    productId: string;
    price: Money;
    /** system-assigned — not supplied by the triggering command */
    designatedAt: utcDateTime;
  }
  // ... Views / Commands interfaces
}
```

The binding-file convention ([em#447](https://github.com/milehimikey/em/issues/447)) puts
everything protocol-shaped in files *next to* the contract, in the same compilation:

```
api/
  main.tsp          # imports the contract + the binding files
  contract.tsp      # symlink/copy target of <model dir>/contracts/<key>.tsp — never edited
  augments.tsp      # em-contract augment output: correlation/header decorators
  binding.tsp       # hand-authored: routes, channels, envelopes, error shapes
  tspconfig.yaml    # your emitters: @typespec/openapi3, typespec-asyncapi, ...
```

TypeSpec's augment decorators (`@@decorator(Target.path, ...)`) attach metadata to
declarations from the *outside*, so the binding can say
`@@format(Pricing.SellingPriceDesignated.priceId, "uuid")` or
`@@correlationId(...)` without touching the generated file. Generic wrappers
(`model Envelope<T> { data: T; }`) let binding-owned ops reference contract models without
re-declaring their shapes. When the model changes, `em api generate` regenerates the
contract; a binding whose augment targets vanished **fails to compile** — drift is a compile
error, not a silent fork.

## `em-contract augment`

The shipped v0 command. It reads an `em export` document and generates the augment file for
the model's async metadata — the part of a binding that is mechanically derivable from the
model rather than authored.

```bash
# 1. in your model repo (or anywhere em runs)
em export models/pricing/pricing.em -o pricing-export.json

# 2. generate candidates (commented out — review, then activate)
em-contract augment pricing-export.json

# 3. or generate live decorators wired into a binding project
em-contract augment pricing-export.json --active \
  --contract ./contract.tsp -o api/augments.tsp
```

| Flag | Effect |
|---|---|
| `-o, --out <path>` | Write to a file instead of stdout |
| `--active` | Emit decorator lines active instead of commented-out candidates |
| `--contract <path>` | Relative path to the generated `.tsp`, emitted as an `import` line |

### What it derives, from what

em's DSL lets an event declare DCB (Dynamic Consistency Boundary) tag keys — the metadata a
consistency-boundary-aware event store keys its streams on. `em export` carries them per
event (`tags`, plus `tag`/`assigned` per field); `em api generate` carries them only as doc
comments (decorators would need a library, and the contract stays dependency-free). em#446
explicitly leaves generating the decorators to this tool. The mapping:

| Model fact (export JSON) | Augment output |
|---|---|
| identity tag field on a public event | `@@header(Ns.Event.field);` candidate |
| the event's *first* identity tag | additionally `@@correlationId(Ns.Event.field);` (AsyncAPI allows one correlationId per message; the typespec-asyncapi idiom is `@header @correlationId` on the same field) |
| composite tag (`tag k from a, b`) | comment note — a computed key has no declared field to augment; derive it at publish time |
| external tag (`tag k external "…"`) | comment note carrying the description |
| `assigned` field on a public event | comment note (system-assigned — not supplied by the triggering command) |
| tagged but **non-public** event | stderr warning — it is not in the contract, nothing is emitted (mark it `public` to bind it) |

Example output (`--active`, for the contract above):

```typespec
// GENERATED by em-contract augment — review candidates, then own this file.
// Source: pricing.em (em export schema 1.20)
// Contract: namespace Pricing (em api generate)
import "typespec-asyncapi";
import "./contract.tsp";
using AsyncAPI;

// event "Selling Price Designated" -> model Pricing.SellingPriceDesignated
@@correlationId(Pricing.SellingPriceDesignated.priceId); // DCB identity tag `priceId`
@@header(Pricing.SellingPriceDesignated.priceId); // DCB identity tag `priceId`
@@header(Pricing.SellingPriceDesignated.productId); // DCB identity tag `productId`
// DCB composite tag `productPrice` from productId, priceId — computed key; derive it at publish time (no augment target).
// Pricing.SellingPriceDesignated.designatedAt is system-assigned — not supplied by the triggering command.
```

Compiled together with the contract and your channel/operation declarations, the
[typespec-asyncapi](https://www.npmjs.com/package/typespec-asyncapi) emitter turns this into
an AsyncAPI 3.0 document whose correlation ids and headers came from the event model — one
source of truth, no copied shapes. (That exact compile — generated augment + generated
contract + typespec-asyncapi — runs as a test in this repo.)

### Guarantees

- **Deterministic**: output is a pure function of the export document and flags — no
  timestamps, no tool version, no absolute paths. Re-running on the same export is
  byte-identical, so the file is diffable and CI-checkable.
- **Honest about naming**: emitted targets (`Pricing.SellingPriceDesignated.priceId`) use
  the same PascalCase + collision-dedupe sequence `em api generate` uses, pinned by tests
  against real generated contracts. When `em api surface --json`
  ([em#448](https://github.com/milehimikey/em/issues/448)) ships, em-contract will consume
  it and stop re-deriving the surface at all.
- **em house rules**: clean stdout (the artifact), diagnostics to stderr, exit 1 with a
  pointed message on a non-export document, version read from package.json at runtime,
  no LLM/AI calls anywhere.

## Integration points with em, by release

| em surface | status | em-contract use |
|---|---|---|
| `em export` JSON (schema 1.x) | shipped (em 1.21) | `augment` input today |
| `em api generate` contract | shipped (em 1.21) | the augment/binding target |
| `em api check` | shipped (em 1.21) | keeps the contract current; em-contract trusts it |
| #444 formatted scalars, #445 command payload models, #446 `interface Events` ops | em 1.22 Wave 1 (in flight) | unlock `bind init` / `bind check` — payload models and Events ops are what make commands and channels augmentable |
| #448 `em api surface --json` | em 1.22 | replaces the export-walking in `src/exportDoc.ts` (seam marked in the module header) |
| #447 binding-file convention docs | em 1.22 Wave 2 | the convention `bind init` will scaffold |

### Planned commands (deliberately not built yet)

- **`bind init`** — scaffold `main.tsp` / `binding.tsp` / `tspconfig.yaml` around an
  existing contract path.
- **`bind check`** — compile contract + binding and verify the binding stays honest:
  every augment targets a declaration that still exists, binding ops reference contract
  payload models instead of shadowing their shapes, compile errors surface as drift
  findings. The compiler groundwork is proven —
  [docs/spike-compiler-api.md](docs/spike-compiler-api.md) (verdict: GO) — but the rules
  want em 1.22 Wave 1's contract shape and the drift-check sample from the em#443 reporter,
  so building them now would mean building them twice.

## Development

```bash
npm install
npm test          # vitest: golden files + the living compiler-API spike
npm run build     # tsc -> dist/
npm run typecheck
```

- `src/exportDoc.ts` — export-JSON reading, public-surface walk, contract-name derivation
  (mirrors em's emitter; the #448 seam).
- `src/augment.ts` — the pure augment builder (`buildAugment`): all mapping rules, no I/O.
- `src/cli.ts` — commander wiring only.
- `fixtures/` — committed `em export` / `em api generate` output (em 1.21.0, export schema
  1.20) with regeneration commands in `fixtures/README.md`; tests never require em.
- `test/golden/` — byte-exact expected augment outputs.
- `test/spike.compiler-api.test.ts` — the compiler-API spike, kept alive as tests.

When em 1.22 Wave 1 regenerates contract shapes (#444/#445/#446), regenerate `fixtures/` and
`test/golden/` in one pass; the naming tests will catch any emitter naming change.
